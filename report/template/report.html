Part 1 · Software Maintenance

1. Introduction & Project Overview

Section 1

Subject system. The subject of this lab is the backend of Jamia as-Suffah, a website for an Islamic educational institution. It is a REST API written in Node.js with Express 4 and Mongoose 8 (MongoDB), deployed as a serverless function on Vercel. Users register and log in (the session is a JWT stored in an HTTP-only cookie); the main feature is a multilingual question-and-answer store in which each question carries English, Bengali and Arabic translations (en/bn/ar) and a list of tags, and can be filtered by tag or searched by title. A seminar model and a Cloudinary upload helper exist but are not yet wired to any route. At the start of this lab the code base had JavaScript files and source lines, 18 commits between January and March 2025, and no tests, README or design documents.

Why this system. It is small enough to understand completely, but it is a real project with real, unplanted defects: one malformed cookie can terminate the server, the server cannot start on current Node.js releases, passwords are written to the log, and error handling is copied by hand into each controller. Every maintenance activity below targets one of these, found by reading the code, running it, and reading its git history. The project's own last commits ("fix: add try catch block in login function", "refactor: comment out cookie setting in login response") show the developers already struggling with the same areas.

2. Methodology

Section 2

Software maintenance is conventionally divided into four categories (ISO/IEC/IEEE 14764): Corrective (repair a fault that causes failures), Adaptive (keep the software usable in a changed environment), Preventive (remove latent faults before they cause failures) and Perfective (improve maintainability or performance without changing behaviour). For each category, this lab made one deliberately small, self-contained change and documented it with the same five steps:

  1. Program Comprehension: read and run the relevant code until the problem and its cause are understood.
  2. Change Management: record a change request: id, category, risk, files touched, and the decision taken.
  3. Impact Analysis: identify every file, caller and behaviour the change can affect.
  4. Reverse Engineering: reconstruct the undocumented design knowledge (flows, contracts, dependency chains) the change relies on.
  5. Refactoring (Implementation): apply the minimal change and verify it with real tooling.

Test first. Before any change, a Jest + supertest suite was added that records the current behaviour. Every bug found during comprehension was written down as a test.failing: a test that states the correct behaviour and is expected to fail. Jest reports such a test as passing while the bug exists and as failing once the bug is gone, so each fix is proven by flipping its test to a normal test. For changes that add new expectations, the new tests are also run against the previous version's source to show that they fail there.

Traceability. Each change is one commit with its own git tag, so every "before" and "after" in this report is a real, checkable version of the project:

4. Corrective Maintenance

Repair a fault

1 · Program Comprehension

isAuthenticated (src/middlewares/auth.middleware.js) guards three routes. It reads the token cookie, verifies the JWT, loads the user and calls next(). Reading it next to Express 4's middleware contract shows two faults on the failure paths:

  • No cookie: line 9 returns a new ApiError but never sends it. Express ignores a middleware's return value, so no response is ever written and no next() is called. The client waits until it times out.
  • Invalid or expired token: jwt.verify throws, and the catch block on line 17 throws again. Because the middleware is an async function, this becomes a rejected promise. Express 4 does not look at promises returned by middleware (only Express 5 does), so the rejection is unhandled. Since Node.js 15 an unhandled rejection terminates the process.

The second fault is severe: a single request with any malformed or expired cookie stops the server for every user. Running the original code confirms both faults.

Before: the first request gets no response; the second terminates the server (exit code 1) with the ApiError from line 17 as the uncaught error.

2 · Change Management

Change idTypeRiskFiles touched
CM-COR-01CorrectiveLowauth.middleware.js (1)

Send both 401 responses with the existing ApiError.send(res) instead of returning or throwing them, and move next() out of the try block. The valid-token path is unchanged. Upgrading to Express 5 (which forwards rejected promises) was rejected for this change: it is a major-version migration with its own breaking changes, far larger than the fault.

3 · Impact Analysis

  • Direct: the three routes that use the middleware, POST /api/auth/logout, GET /api/auth/profile and GET /api/protected-route. Requests with a valid token behave exactly as before.
  • Clients: requests that used to time out or break the connection now receive 401 with the standard error body {success, message, errors}, the same shape as every other error the API returns.
  • Indirect: with next() outside the try, an error thrown synchronously by a later handler is no longer caught and misreported as "Invalid or expired token"; it now reaches the error handler.
  • Residual: a valid token for a deleted user still passes with req.user = null. This is recorded, not fixed here.

Adjust to a changed environment

The project's environment moved on without it. Node.js 25 removed SlowBuffer, an API deprecated for years (DEP0030), and current Node.js releases (this machine runs 26) no longer have it. Starting the unmodified server under Node.js 26 fails before a single line of application code runs:

Before: the server cannot start on Node.js 26.

The stack trace leads into node_modules, not src/. The application never uses SlowBuffer itself; a transitive dependency of jsonwebtoken does, at import time:

This is adaptive maintenance in its purest form: the code did not change and was not wrong when written. The runtime it depends on changed underneath it.

6. Preventive Maintenance

Fix latent faults before they cause failures

1 · Program Comprehension

Following the password through the authentication code reveals three latent faults. None has caused a visible failure yet, which is what makes this preventive rather than corrective work, but each one leaks a credential:

  • registerUser starts with console.log(req.body), writing every new user's plaintext password to the server log (on Vercel, readable by anyone with access to the project's logs).
  • loginUser logs JSON.stringify({user, token}): the bcrypt hash and a valid session token.
  • Both endpoints return the full user document, including the bcrypt hash, in the response body. A leaked hash can be attacked offline without any rate limit.
Before: the hash appears in both responses; the server log contains the plaintext password, the hash and the token (log truncated).

2 · Change Management

Change idTypeRiskFiles touched
CM-PRE-01PreventiveLowuser.model.js, auth.controller.js (2)

Remove the two logging statements that print credentials, and strip password when a User document is converted to JSON, in the schema itself. Deleting the field in each controller was rejected: it would fix today's two routes but not the next route that returns a user. A schema-level rule protects routes that do not exist yet, which is the point of preventive maintenance.

3 · Impact Analysis

  • Direct: every response that serialises a User: register, login, profile and the protected route.
  • Unaffected: storage and authentication. comparePassword reads the field from the document, not from JSON, and the pre-save hashing hook is untouched.
  • Clients: no legitimate client needs the hash; the token is still returned and set as a cookie.
  • Operations: the server log loses the request-body line. loginUser still logs the email address (personal data, recorded as residual).

4 · Reverse Engineering

A source-to-sink data-flow map of the password, recovered from the controller, the model's hooks and Express's JSON serialisation:

7. Perfective Maintenance

Improve structure without changing behaviour

1 · Program Comprehension

The code has two competing error-handling mechanisms. asyncHandler forwards any rejected promise to the global error handler in app.js, but that handler ignores ApiError and always answers 500. To get the right status codes anyway, three controllers wrap their entire body in the same hand-written try/catch that rebuilds the error and sends it. The clone detector finds the copies:

Before: two clone pairs of the 8-line catch block (and one acceptable clone in the models, discussed in §16).

The duplication is a design fault, not just untidiness: correct behaviour depends on remembering to copy the block. registerUser has no copy, so its "user already exists" error, an ApiError(400), reaches the global handler and becomes a 500. getQuestions passes its 404 message in the wrong argument and relies on the catch block's fallback text.

2 · Change Management

Change idTypeRiskFiles touched
CM-PER-01PerfectiveMedium (every error path)app.js, auth.controller.js, question.controller.js (3)

Make the global handler the single place where errors become responses: it sends an ApiError with its own status and body, and answers anything else with a generic 500 in the same shape. Then delete the three copied try/catch blocks, since asyncHandler already forwards errors. Fix the argument order of the one 404 that relied on the old fallback.

Residual findings

Comprehension and analysis surfaced more problems than one change per category can address. They are recorded here rather than fixed silently, so that each change above stays small and traceable:

  • Tags are never stored. createQuestion puts tags inside the translation instead of on the question, so tag filtering never finds questions created through the API (two test.failing tests; confirmed at runtime in §15).
  • Missing fields pass validation. field?.trim() === "" is false for undefined, so absent fields reach Mongoose and produce a 500 instead of a 400.
  • Unescaped search. ?search= goes straight into $regex: special characters cause a 500, and crafted patterns risk regular-expression denial of service.
  • No authorisation on question creation. POST /api/questions/add is open to anonymous clients.
  • Lint findings (§12): a duplicate secure key in the login cookie options makes the intended NODE_ENV-dependent setting dead code; two unused variables.
  • Dependencies: npm audit still reports vulnerabilities ( critical, in mongoose and proxy-addr; others in express, body-parser, cloudinary, lodash, path-to-regexp, qs). All have fixed versions available.
  • Smaller items: the login email is logged; a token for a deleted user passes authentication with req.user = null; cors() with default options cannot serve credentialed cross-origin requests from a separate frontend.

Conclusion

Each category produced a change of a different character: a fault visible to every user (corrective), a failure caused only by the environment moving on (adaptive), risks that had not yet caused harm (preventive), and a structural weakness that was quietly producing wrong status codes (perfective). The five-step process kept each change small: comprehension located the cause, impact analysis bounded what could break, and reverse engineering recovered the design knowledge the change depended on. The test-first approach made every claim checkable: each fix is a known-bug test turning into a passing test, at a tagged commit anyone can check out.

11. Static Analysis A: AST Generation

Section 11

An Abstract Syntax Tree represents source code as a tree: each node is a construct (a declaration, a call, an identifier) and each edge says which construct contains which. Static analysis tools work on this tree rather than on text. The first statement of the authentication middleware, dumped in the same style as Python's ast.dump:

One statement and its AST.

Reading the output. const token = req.cookies.token; is a VariableDeclaration of kind const with one VariableDeclarator. Its id is the name being defined (token) and its init is the value: a MemberExpression whose object is another MemberExpression (req.cookies). Property access nests from the inside out. The slicer in §14 uses exactly this distinction: id is a definition, identifiers inside init are uses.

The whole isAuthenticated function as an indented tree (final version). The IfStatement and TryStatement nodes are the branches discussed in §4.

14. Program Slicing (Static & Dynamic)

Section 14

A slice is the set of statements that can affect the value of a variable at a chosen point, the slicing criterion. A static slice considers every possible execution; a dynamic slice only the statements that affected the value in one particular execution, so it is usually smaller. tools/slice.mjs computes backward slices inside a function by following two kinds of dependency:

  • Data: a statement that uses variable v depends on earlier statements that define v (for query.tags = …, the object query counts as both used and defined).
  • Control: a statement depends on the if or loop test that decides whether it runs, including an earlier if (…) { return/throw } that can skip it.

Criterion: the MongoDB query object query at line of getQuestions, where it is passed to Question.find. This is the question a maintainer asks when a search returns the wrong questions: which code decides what is searched for?

Static slice: everything that may shape the query.

The static slice keeps both filters, the tag filter (lines 36–38) and the title search (42–43), and the destructuring of req.query that feeds them; logging, the 404 check and the response are excluded. For the dynamic slice, one test, "searches titles case-insensitively" (GET /api/questions?search=PRAYER), was run alone with coverage, and the slicer was restricted to the statements that executed:

Running the single test that defines the execution. Dynamic slice for that execution (· marks lines that did not run).

Insight. The dynamic slice drops the tag branch completely. The if (tags) test did run (it evaluated to false) but is not in the slice, because nothing it controls contributed to query. That is the defining difference from coverage: coverage says what ran, the slice says what mattered. In maintenance terms, a bug report about title search can be investigated in five statements instead of twelve. The same slice explains the residual tags bug: query.tags filters the top-level tags field, which the static slice of createQuestion would show is never written.

Limitations: the slicer works inside one function, does not do kill analysis (every earlier definition counts), and treats a method call obj.m(…) as possibly modifying obj. These over-approximate, so the slices may be larger than necessary but do not miss statements in code of this shape.

15. Runtime Analysis: Tracing & Profiling

Transformation tools (Lab 3)

The lab's transformation tools turn a running program into a readable form: a log (Loguru), a line-by-line trace (PySnooper), a timeline or a chart of where time goes (VizTracer, cProfile + SnakeViz). For this server, the useful unit of execution is an HTTP request and the database work it causes. tools/workload.mjs loads the unmodified application, wraps it in a request logger, enables Mongoose's query hook, and replays a scripted session. Passwords' hashes and tokens are masked in the output.

Request/query trace of the final version, in Loguru's time | level | message format.

Insights from the trace.

  • Registration costs three database operations, including a createIndex issued by Mongoose on the first write to users; the unique e-mail index is created lazily, not by a migration.
  • Login takes ~70 ms against ~2–5 ms for every other request, all of it before the database reply is used: password hashing (see the profile below).
  • The profile lookup excludes the password at the query level (projection: {password: 0}), and the forged token is rejected in under a millisecond with no database query: the CM-COR-01 path.
  • The insertOne for the new question stores "tags": [], and the next request's tag query returns 404. This is the residual tags bug observed at runtime, not just inferred from the code.

CPU profiling

V8's sampling profiler (node --cpu-prof) records the call stack every millisecond. A workload of 30 rounds of login, profile, add question and search was profiled; tools/profile.mjs summarises the profile by package and function (the cProfile view) and draws an icicle chart of the call tree (the SnakeViz view).

Profile summary of the final version. Icicle chart of the CPU profile. Each box is a function in a call path; its width is the time spent in it and its callees; callees sit beneath their caller. Orange: application code (src/).

Insight. % of CPU time is spent inside bcryptjs, and comparePassword, called once per login, accounts for % of the whole workload. The application's own code is negligible. This is by design: bcrypt with cost factor 10 is meant to be slow, to make stolen hashes expensive to crack. It is not a defect, but it is a capacity limit worth knowing. Login throughput on one core is bounded at roughly a dozen per second, and bcryptjs is a pure-JavaScript implementation that blocks the event loop while hashing. A native binding (bcrypt) or moving hashing to a worker thread would be the perfective options if login load grew.

16. Code Clone Detection

Lab 6

Tool overview. jscpd tokenises each file, slides a window over the token stream, and hashes each window (Rabin–Karp); windows with equal hashes in different places are reported as clones once they reach the minimum size. Because it compares tokens, not characters, formatting differences do not hide a clone. It was chosen for its JavaScript support, its precise locations, and its JSON output (used for the numbers below). Thresholds: at least 5 lines and 30 tokens.

Method. jscpd was run on src/ at baseline, the clones were inspected, the refactoring was applied (CM-PER-01), and the same command was run on cm-per-01.

Caveats.

  • Coverage shows what ran, not that it is correct; and percentages of two versions have different denominators (§13).
  • Cyclomatic complexity counts decision points; it says nothing about how hard the code is to read.
  • The slicer is an approximation (§14); results were checked by hand against the source.
  • Profile numbers depend on the machine and the workload; the shares (bcrypt dominates) are stable, the milliseconds are not.
  • jscpd only finds clones above its thresholds and does not find semantic (Type 4) clones.
  • Timestamps, ids and timings in the terminal panes change on every regeneration; the conclusions do not.
